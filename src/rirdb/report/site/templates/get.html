In order of effort. Whichever you use, the files come from the original host, and each dataset keeps its own licence.

  1. From the source

    Each dataset page gives the homepage, the repository record, the DOI and every file with its size and checksum. Download by hand from there.

Fetch scripts

Every dataset in the registry has a script at get/<id>.sh. It is plain bash, readable from top to bottom: the header gives the licence, the source, the number and size of the files and the date rirdb resolved them. Choose a dataset to see the commands.

{{ ex.id }}.sh Dataset page 
{{ pick_tpls[ex.pick] | replace("__ID__", ex.id) }}

The commands change with the dataset: a script for a manual download prints instructions and downloads nothing, and a source without a lock file has no rirdb checksums to check against.

Several datasets in one go (here the {{ small3 | length }} smallest with provider checksums):

{{ m.code("for id in " ~ small3 | join(" ") ~ "; do\n curl -fLO " ~ SITE_URL ~ "get/$id.sh\n bash $id.sh ~/datasets\ndone", "many") }} {% endif %}

What a script does

  • Creates <target_dir>/<id>/ and downloads every file in the dataset's lock file from the original host with curl -L --fail --retry 3 -C -: it follows redirects, retries, and resumes a partial file where the host allows it. GitHub's archive server does not, so an interrupted GitHub archive is downloaded again from the start.
  • Writes the checksums next to the files (checksums.md5, checksums.sha256) and checks each file with md5sum -c or sha256sum -c. Files that already verify are skipped, so running it again is safe.
  • Rejects a web page sent in place of a file (a firewall or login page), and warns when the disk has less free space than the files need.
  • Does not extract archives and deletes nothing it did not download. At the end it prints the commands that extract the archives the way rirdb does, so the paths match rirdb's manifest, and the command that checks every extracted file against it.
  • Stops with a non-zero exit status when a file fails, so it can run inside a batch job.

It needs bash, curl and GNU coreutils (on macOS: brew install coreutils). Some sources need one more tool:

The rirdb pipeline

The pipeline downloads, checks, indexes and analyses datasets; it is what this site is built from. The registry (one folder per dataset, registry/<id>/dataset.yaml) says where each dataset comes from, and the committed lock files and manifests pin exactly which files.

{{ m.code("git clone " ~ REPO_URL ~ "\ncd room-impulse-responses\n# once; the override lets the GPU build install on a machine without a GPU\nCONDA_OVERRIDE_CUDA=12.6 pixi install\n# set RIRDB_ROOT: where the audio, the index and the metrics go\ncp .env.example .env", "pipe-install") }}

On a SLURM cluster

On Apocrita every step runs as a batch job, Python included (see docs/hpc.md). The download layer is bash only.

{{ m.code("# resolve, download, extract and list the files of every dataset in wave 1\nsbatch jobs/download.sh fetch/run.sh --wave 1\n# two datasets, keeping the committed lock files as they are\nSKIP_RESOLVE=1 sbatch jobs/download.sh fetch/run.sh ace rochester\n# check every file against its manifest\nsbatch jobs/quick_cpu.sh pixi run rirdb dev verify --wave 1 --full\n# summarise what is in the files, then index them (one row per IR)\nsbatch jobs/quick_cpu.sh pixi run rirdb dev probe ace\nsbatch jobs/quick_cpu.sh pixi run rirdb dev index-v1 ace\n# the analysis as a SLURM array of 4 shards, then the merge\njobs/analyze_dataset.sh ace 4", "pipe-slurm") }}

Anywhere else

Without SLURM the same scripts run in plain bash. The download layer needs bash, curl, jq, unzip, zip and tar, and wget for a mirrored web folder; 7-Zip comes with the pixi environment.

{{ m.code("set -a; source .env; set +a\nSKIP_RESOLVE=1 bash fetch/run.sh ace rochester\npixi run rirdb dev verify ace rochester --full\npixi run rirdb dev probe ace && pixi run rirdb dev index-v1 ace\npixi run rirdb dev analyze --dataset ace && pixi run rirdb dev merge ace", "pipe-plain") }}

Without SKIP_RESOLVE=1, fetch/run.sh asks each provider for its current file list first, rewrites the lock file, and warns if a provider's checksum changed. Datasets are grouped in download waves; --wave N selects the datasets of a wave that are open and active or planned, and leaves out the deferred, broken and manual ones.

Checking files: lock files and manifests

Two files describe each dataset rirdb downloaded. The lock file lists what to download, with the provider's checksum or one rirdb recorded. The manifest lists every file after extraction, with its sha256. Both are tab-separated text with a header row; manifests are gzipped. They are here as data/locks/<id>.lock.tsv and data/manifests/<id>.files.tsv.gz, linked from the table above and from each dataset page.

Checking by hand

Run these in the dataset folder. md5sum -c and sha256sum -c read lines of the form checksum, two spaces, file name; awk turns the lock or the manifest into that form.

{% set lk = "$site/locks/" %} {% set mn = "$site/manifests/" %} {% set cmds = "site=" ~ SITE_URL ~ "data\n\n# the downloaded files against the md5 rows of a lock file (" ~ ex.id ~ ")\ncurl -fsSL " ~ lk ~ ex.id ~ ".lock.tsv \\\n | awk -F'\\t' 'NR > 1 && $4 == \"md5\" { print $5 \" \" $1 }' \\\n | md5sum -c -\n" %} {% if ex_sha %}{% set cmds = cmds ~ "\n# the same with sha256 rows (" ~ ex_sha.id ~ ")\ncurl -fsSL " ~ lk ~ ex_sha.id ~ ".lock.tsv \\\n | awk -F'\\t' 'NR > 1 && $4 == \"sha256\" { print $5 \" \" $1 }' \\\n | sha256sum -c -\n" %}{% endif %} {% set cmds = cmds ~ "\n# every file after extraction against the manifest (" ~ ex.id ~ ")\ncurl -fsSL " ~ mn ~ ex.id ~ ".files.tsv.gz \\\n | gunzip | awk -F'\\t' 'NR > 1 { print $3 \" \" $1 }' \\\n | sha256sum -c --ignore-missing --quiet -" %} {{ m.code(cmds, "verify-cmds") }}

With --quiet only problems are printed; drop --ignore-missing to list the files you do not have as well. A fetch script leaves checksums.md5 or checksums.sha256 in the dataset folder, so md5sum -c checksums.md5 re-checks a copy at any time. Paths in a manifest assume the archives were extracted as rirdb does: in place when the dataset has one archive, into a folder named after each archive when it has several. The fetch scripts print these commands.

Extracting archives

The fetch scripts do not extract archives; at the end they print the exact commands for the dataset. rirdb extracts them as fetch/extract.sh does, and the manifests assume that layout:

  • A dataset with one archive is extracted in place: unzip -q <name>.zip -d . or tar -xf <name>.tar.gz (also .tgz, .tbz2, .tar.bz2, .tar.xz).
  • A dataset with several archives gets one folder per archive, named after it, because archives of one dataset can hold the same file names: unzip -q <name>.zip -d <name>.
    • {% if split_ids %}
  • A split zip (.z01, .z02, … with a .zip) is joined first: zip -s 0 <name>.zip --out <name>.joined.zip, then unzipped. In the registry: {% for i in split_ids %}{{ by_id[i].name if i in by_id else i }}{{ ", " if not loop.last }}{% endfor %}.
    • {% endif %} {% if big_zip %}
  • Zips over 4 GiB need ZIP64 records. Info-ZIP's zip-bomb check can reject a large, valid zip, so rirdb unzips archives that passed their checksum with UNZIP_DISABLE_ZIPBOMB_DETECTION=TRUE. If unzip still fails, try 7-Zip (7z x); if that fails too, zip -FF <name>.zip --out <name>.repaired.zip rebuilds the zip directory from the local headers{% if repaired %} (rirdb needed this for {% for r in repaired %}{{ r.name }}{{ ", " if not loop.last }}{% endfor %}){% endif %}. {{ big_zip | length }} datasets have zips over 4 GiB: {% for b in big_zip %}{{ b.name }} ({{ b.n }} file{{ "s" if b.n != 1 }}, largest {{ b.bytes | bytes }}){{ ", " if not loop.last else "." }}{% endfor %}
